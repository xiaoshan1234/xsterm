# dev/flows — 代码流程文档

> **定位**：与 `adr/`（"为什么这么选"）互补，**面向"代码怎么做"**。
> 每篇文档讲一个完整用户动作的端到端代码调用链，从前端 invoke 一直到 tokio task / OS 调用，配 ASCII 流程图 + `path:line` 引用。

## 何时读 / 何时写

| 我想……                     | 看                                                                                        |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| 理解某段代码的真实执行路径 | 这目录对应流程                                                                            |
| 排查"卡哪一步了"           | 流程图 + 路径对照日志 `[DEBUG-...]` 标记                                                  |
| 写新文档                   | 参考现有文件的结构（1. 流程图 → 2. 调用栈表 → 3. 关键时序 → 4. 错误路径 → 5. 跨视图引用） |
| 想看"为什么这么设计"       | `dev/adr/`                                                                                |
| 想看"未来要变什么"         | `dev/roadmap/`                                                                            |

## 命名约定

`NN-verb-noun.md`，按时间顺序编号：

- `NN` = 两位数（01, 02, ...）
- `verb-noun` = 动作 + 对象的英文小写连字符

例：`01-open-tmux-session.md`、`02-split-tmux-pane.md`

## 模板

每篇流程文档包含：

1. **一句话**：这个动作做什么
2. **入口点**：用户操作的 UI 元素
3. **ASCII 流程图**：从前端到 backend 到 OS
4. **调用栈表**：每一步的 `path:line` + 关键行为 + 日志关键字（方便 grep）
5. **关键时序**：async 边界 / channel 同步点
6. **错误路径**：每一步的可能失败模式
7. **跨视图引用**：连到 `architecture/` 4+1 视图的对应章节

## 维护规则

- 代码结构变（新增模块 / 改调用链 / 改 channel 拓扑）→ 同步更新对应流程文档
- 流程文档**不复述** ADR 的"为什么"（指向 adr/）
- 流程文档**不画** UML（用 ASCII 流程图，跟 `architecture/` 风格一致）
- 流程文档**保留** `path:line` 引用 —— 这是 dev 排查时的 ground truth
